# MediQ

Online doctor appointment platform (India first, global-ready).
Patients pick a hospital, department, doctor and slot, pay online and get a token number instantly.

```
apps/
  web/   Next.js (App Router) + TypeScript + Tailwind, PWA. UI only, no business logic.
  api/   Express + TypeScript REST API (/api/v1), Zod validation, Prisma. Reused by the future mobile app.
prisma/
  schema.prisma   Database source of truth
  migrations/     Generated by `pnpm db:migrate`
```

## Status: Phase 8 (Growth) done

**Phase 8**

- **Reviews and ratings.** Only the patient who booked a visit online can review it, once, after it was **completed**,
  within 30 days (`REVIEW_WINDOW_DAYS`). They can change it for 7 days and delete it any time. The public sees
  stars and comments with **first name and last-name initial only** ("Sunita S."), on doctor and hospital pages and in
  search. A hospital **cannot hide or change** a review: it can only **report** it; the platform admin hides it,
  restores it or dismisses the report (Admin > Reviews). Everything is in the audit log.
- **Waitlist.** When every slot of a doctor's day is full a patient can join the waitlist for that day (up to 5 days at a
  time). When a seat opens (a cancellation, a hold that ran out) the **oldest waiting patients are told by SMS**, a few
  at a time. **The seat is not held**: whoever books first gets it. A patient who does not book within an hour
  loses their place to the next one; days that pass end the wait.
- **Search and filters** (`/search`). Words (every word must match a name, speciality, qualification, department,
  hospital or city), then city, speciality, language, doctor's gender, rating, fee, and "a seat is free on this day".
  Sort by recommended (ratings weighed by how many reviews there are), earliest appointment, rating, fee or experience.
  Every doctor shows their rating and **next free seat**. `/public/hospitals` also filters by speciality and emergency line.
- **Patient history** (`/patient/history`). Every visit across hospitals and family profiles, with a summary (visits,
  doctors, hospitals, what was paid after refunds), by person and year, and a way to rate a visit or book again.
- **Hindi.** A language switch (English | हिन्दी) on every page, remembered in the browser and, for a patient, on their account.
  **The patient's SMS are sent in Hindi too** (booking, reminder, cancellation, reschedule, waitlist, blood alerts). The
  web texts are translated for the home page, navigation, appointment statuses, search, reviews, waitlist and history;
  **other screens stay English for now** (they fall back to English, nothing breaks). Messages from the API (error texts) are English.
  **Have a native speaker review the Hindi** (`apps/web/src/lib/i18n/messages.hi.ts` and the SMS texts) before launch.
- **Subscription plans for hospitals.** A plan sets how many **doctors**, **staff logins** and **online bookings a month** a
  hospital can have, and whether it gets **analytics** and **slip printing**. **The platform admin assigns plans and
  records payments received offline** (bank transfer, UPI, cash, cheque); there is no card billing. A plan can start with a
  trial, runs for the months paid, has **7 grace days** (`SUBSCRIPTION_GRACE_DAYS`) after it ends, and then **online bookings
  stop** (existing appointments, the desk and the hospital's own panel keep working). Admins can suspend, cancel and resume.
  New hospitals start on the free **pilot** plan; a hospital with no subscription row is unrestricted.
- **Not in this phase** (decided with you): the mobile app (its own phase later), tele-consultation, digital prescriptions.

**Phase 7**

- **Blood banks** register themselves with a **licence number** (their contact phone is proved with a code). They are
  **not listed and cannot operate until the platform admin verifies the licence** (Admin > Blood banks: approve,
  reject with a reason, block). A rejected bank fixes its details and resubmits. Staff manage their own bank's stock
  by blood group, donations and colleagues' logins.
- **Public finder** (`/blood`): verified banks by city, blood group, "in stock only" and distance. Stock older than a
  day is shown as "call to confirm".
- **Donors**: a patient registers as a donor (`/patient/donor`) after agreeing to alerts, with an availability toggle.
  The **waiting period between donations is about 3 months for men and 4 months for women and anyone who prefers not
  to say** (90 / 120 days, set in `.env`), and age is limited to 18 to 65.
- **Donations are created only by blood bank staff**: they find the donor by phone, record the group their own test
  found, and the donor's waiting period starts. A mistaken record can be voided within 48 hours. **There are no
  coupons or vouchers: a donation is a dated record, nothing is issued to the donor and nothing is redeemed.**
- **Emergency blood requests** (`/blood/request`): anyone can ask, after a code sent to their phone, with limits (3 a
  day per number, no duplicates, per-address limits). Donors of the **same blood group** within the chosen radius and
  nearby verified blood banks are alerted by SMS. **Only after a donor taps "I can help" does the requester see
  that donor's number** (and only while the request is open). Donors never see the requester's number.
- A clear **disclaimer** on every blood screen: MediQ only connects people; availability and safety are the blood
  bank's responsibility.

**Phase 6**

- **Security review as tests.** Every endpoint is read from the real router (`pnpm routes` prints them). Tests
  fail if any endpoint outside a short public list lacks a login or a role gate, and a malformed-input test sends
  broken paths, bodies and query strings to **every** endpoint (as the right role, the wrong roles, and with forged
  tokens): none may answer with a server error or leak internals.
- **Security headers:** API (HSTS, Permissions-Policy, helmet, no caching, strict CORS allow-list) and web (HSTS,
  frame blocking, and a **report-only** Content-Security-Policy to enforce after a clean pilot week).
- **Sentry** for the API and the web app, off unless a DSN is set; only genuine crashes are sent, with names,
  phone numbers, request contents and addresses removed.
- **Daily encrypted database backups** (`pnpm db:backup`, a scheduled workflow to a private bucket) and a written
  **restore drill** (`docs/BACKUP-RESTORE.md`).
- **API reference (Swagger)** at `/api/docs` (development; off in production unless `DOCS_ENABLED=true`), built from
  the same validation schemas the API uses. A test fails if an endpoint is undocumented.
- **Admin dashboard** (`/admin`): bookings, cancellation and no-show rates, online money, refunds, commission,
  cash, busiest hospitals, daily charts. **Hospital analytics** (`/hospital/analytics`): the same for one hospital,
  plus doctors, departments, busy hours, average wait and consultation time.
- **Privacy rights:** a patient can download a copy of their data and erase their account (`/patient/privacy`);
  privacy policy updated; consent checkboxes at signup were already in place.
- **Install prompt** (Android, desktop, and an iPhone hint) and a fuller PWA manifest with shortcuts.
- **Guides:** `docs/DEPLOYMENT.md` (Vercel + Render + Neon) and `docs/PILOT-CHECKLIST.md` (5 to 10 hospitals, one city).
- `pnpm admin:create` makes the first platform admin in production (the seed refuses to run there).

**Phase 5**

- **Reception desk** (`/reception`): the day's list with live refresh, walk-in booking (same booking engine as online, so
  no double-booking; cash payment recorded, token still issued), check-in by scanning the ticket QR or typing the
  code, cancel with refund instructions, print slips (one or the whole day).
- **Doctor queue** (`/doctor`): waiting patients in token order, Start / Complete / No-show, "Call next patient".
- **Live queue page** `/q/{doctorQrToken}`: now serving, patients waiting, and an estimated wait (people ahead x the
  doctor's average consultation time). Polls every 5 seconds. Numbers only, no personal details.
- **Slips**: a drag-and-drop template editor (react-rnd) that saves positions in millimetres; a PDF generator that prints
  only the data onto pre-printed paper (Hindi supported), X/Y printer calibration, test print and alignment sheet.
- **Emergency finder** (`/emergency`): call 112, nearest open hospitals with call and directions buttons and bed
  availability, optional Google Maps map.
- **QR codes**: hospital, doctor-queue and booking-ticket codes, downloadable as PNG and printable.

**Phase 4**

- **Razorpay payments.** The pay panel asks the API for an order (created at the server's price), opens Razorpay
  checkout, then waits. The booking is confirmed **only by Razorpay's signed webhook**; nothing the browser says
  can confirm it. Test mode (`PAYMENT_MODE=mock`) still works with no keys.
- **Webhook safety:** signature checked on the raw body, every event stored once (replays do nothing), safe to
  retry, amount checked against the order, out-of-order events can't undo a payment.
- **Failed payments** release the held slot. A payment that succeeds later re-takes the seat if it is free, and is
  **refunded automatically** if it is not (or if the booking was cancelled, or it is a duplicate payment).
- **Refunds by policy**, configurable per hospital (default: full refund if cancelled at least 24 h before, 50% after
  that, none for a no-show, always full when the hospital cancels). Shown to the patient before they pay and
  before they cancel. Refunds are queued with the cancellation and retried until they succeed.
- **Messages** (SMS, or WhatsApp via Twilio) for booking confirmed, rescheduled, cancelled (with the refund
  amount) and a **reminder 2 hours before**. Providers: MSG91 and Twilio behind one interface, plus a console mock.
- **PDF receipt** (₹, refunds shown, Hindi names supported).
- Payments and commission are stored on every payment (`Payment.commissionAmount`).

**Phase 3**

- Patients browse without logging in: hospital search, the hospital page `/h/{slug}` (what the hospital QR opens), a department
  filter, the doctor page, a date strip and time slots.
- Booking: choose who it is for (themselves or a family member), the slot is **held for 5 minutes**, then pay.
  A **token number** (next integer for that doctor on that day) and a **check-in QR** are issued on confirmation.
- My appointments (upcoming / past), an appointment page with the ticket, **cancel** and **reschedule** (same doctor,
  no new payment, new token and QR). Family profiles (add, edit, remove).
- **Never double-books**: tested with 50 simultaneous bookings of one seat, a 100-patient parallel day, concurrent
  token issue and concurrent reschedules, on a real PostgreSQL server (see "Booking engine" below).
- Payment is a **test payment** for now (`PAYMENT_MODE=mock`, no real money). Phase 4 swaps in Razorpay; the booking is
  then confirmed only by the verified webhook, through the same `confirmAppointment()` function the test payment uses.

**Phase 2**

- Admin: list, search, create, edit, approve, block and unblock hospitals. Creating a hospital also creates its
  login with a random temporary password, shown once. The admin can reset it later. Commission % is set per hospital.
- Hospital panel: overview with a setup checklist, departments, doctors (profile, fee, photo upload, optional
  doctor login), weekly timings with several sessions per day, slot length and patients per slot, leaves,
  a slot grid (block or reopen single slots), emergency number and bed count, and receptionist logins (create, reset, block).
- `Slot` rows are generated for the next 30 days from the schedules, minus leaves. They regenerate automatically
  when timings, leaves or a doctor's active status change, from a background job every 6 hours, and on demand.
  Slots that already have bookings are never deleted.
- Photo storage through Cloudinary behind a storage interface. Images are checked by their content and capped at 5 MB.

## 1. Prerequisites

- **Node.js 22.12+** (you have 24)
- **pnpm 10**: `npm i -g pnpm@10`
  On this machine npm's global folder is not on PATH yet. Add it once (PowerShell), then open a new terminal:
  ```powershell
  [Environment]::SetEnvironmentVariable("Path", [Environment]::GetEnvironmentVariable("Path","User") + ";$env:APPDATA\npm", "User")
  ```
- **A PostgreSQL database.** We use [Neon](https://neon.tech) (free tier):
  1. Sign up, then **Create project**. Pick region **AWS Asia Pacific (Singapore)** (closest to India), database name `mediq`.
  2. Open **Connect**. Copy the connection string **with "Connection pooling" ON**: that is `DATABASE_URL`.
  3. Toggle pooling **OFF** and copy again: that is `DIRECT_URL` (used by migrations).
- **Cloudinary** (optional until you need doctor photos): sign up at [cloudinary.com](https://cloudinary.com),
  then copy **Cloud name**, **API key** and **API secret** (Settings > API Keys) into `CLOUDINARY_CLOUD_NAME`,
  `CLOUDINARY_API_KEY` and `CLOUDINARY_API_SECRET` in `apps/api/.env`. Without them, photo uploads answer
  "not configured" and everything else works.

## 2. Setup

```bash
pnpm install                          # also generates the Prisma client
cp apps/api/.env.example apps/api/.env  # skip if apps/api/.env already exists
cp apps/web/.env.example apps/web/.env.local
```

Edit `apps/api/.env`: paste `DATABASE_URL` and `DIRECT_URL` from Neon. Make sure `JWT_ACCESS_SECRET` and
`OTP_HMAC_SECRET` are long random strings (a fresh `.env` created during setup already has random ones). To
generate one:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

Create the tables and load sample data:

```bash
pnpm db:migrate     # applies every migration in prisma/migrations
pnpm db:seed        # sample data + generates ~1,300 slots for the next 30 days
```

## 6. Design notes

- **One `User` table for all roles.** Staff have `loginId` + `passwordHash`; patients have `phone` only.
  Patients and family members are `PatientProfile` rows (relation `SELF`, `CHILD`, ...).
- **Password hashes never leave the database layer.** The Prisma client omits `passwordHash` globally; only the
  login and change-password flows opt in.
- **Immediate revocation.** Every authenticated request re-reads the user. Blocking a user or hospital, or
  changing a password (`tokenVersion` bump), takes effect immediately, not after the token expires.
- **Refresh token rotation** with reuse detection and a 20 s grace window for two tabs refreshing at once.
- **Slots are real rows** (`Slot`: doctor, start/end, capacity, `bookedCount`, status). The generator in
  `modules/slots` is idempotent and safe to run concurrently (per-doctor advisory lock). It never touches past
  slots, keeps manually blocked ones, and never deletes a slot that has bookings; those come back as `conflicts`.
- **Double-booking protection (Phase 3)**: booking locks the `Slot` row (`SELECT … FOR UPDATE`) and checks
  `bookedCount < capacity`. `DoctorDay` holds the token counter. `Appointment` has unique `(slotId, seatNumber)`
  and `(doctorId, appointmentDate, tokenNumber)` as the last line of defence. The concurrency tests must run
  against real Postgres (Neon): the throwaway `prisma dev` database only handles one connection.
- **Temporary passwords** are 12 random characters from an alphabet without look-alikes (`Kp7m-Xq4z-Rt9b`),
  returned once, never logged or audited. Resets and blocks end all of the user's sessions immediately.
- **Money** is integer minor units (paise) plus a currency code. **Times** are `timestamptz`, with a timezone per hospital.
- **Rate limiting**: generous per-IP limits (carrier NAT), strict per-phone and per-account limits enforced in
  the database so they hold across API instances. In-memory store for now; switch to Redis for multiple instances.
- **SMS** goes through `services/sms` (interface + console mock). The API refuses to start in production with
  the mock provider. MSG91/Twilio are wired in with notifications.

### Booking engine (how double-booking is prevented)

Everything is in `apps/api/src/modules/appointments/booking.service.ts`.

1. Each change to a slot's seats runs in **one transaction that first locks the `Slot` row** (`SELECT … FOR UPDATE`).
   Competing bookings wait, then re-check capacity.
2. **Lock order is fixed** (patient, then slots sorted by id, then the appointment, then the token counter), so concurrent reschedules cannot deadlock.
3. An appointment holds a seat **if and only if `seatNumber` is not null**. `Slot.bookedCount` is recomputed from that, never blindly incremented.
4. **Token numbers** come from one atomic `INSERT … ON CONFLICT DO UPDATE … RETURNING` on `DoctorDay`, inside the confirming transaction: unique and gap-free.
5. The unique constraints `(slotId, seatNumber)` and `(doctorId, appointmentDate, tokenNumber)` are the last line of defence.
   In a check with the row lock deliberately removed, five of the race tests failed (winners were rejected rather than double-booked): the tests detect a broken engine, and the constraints held.
6. **Holds** expire after `BOOKING_HOLD_MINUTES` (5). A job releases them every 30 s _and_ the booking transaction releases them inline, so correctness never depends on the job.
7. A **late payment** (hold already expired) re-takes the seat if it is still free; otherwise `confirmAppointment` returns `SLOT_LOST` so Phase 4 can refund automatically.
8. `confirmAppointment()` is **idempotent** (safe for repeated webhooks): one payment row and one token, however many times it is called.

Rules (all configurable in `.env`): booking closes 15 min before the slot, cancel and reschedule close 60 min before, at most 3 unpaid holds per patient, at most 2 reschedules per appointment.
Cancelling does not refund yet: refund rules arrive with real payments in Phase 4.

### Payments, refunds and messages (how they stay correct)

- **Webhook is the only confirmer.** `confirmAppointment()` is called by the verified Razorpay webhook (and by the test payment in development).
  Orders are created by the server at the doctor's fee; a captured amount that differs is flagged (`payment.amount_mismatch` in the audit log) and never confirmed.
- **Money received is always recorded**, whatever becomes of the booking, and anything that can't become a booking
  (slot taken, booking cancelled, second payment) gets a full refund queued **in the same database transaction**.
- **Refunds** are written as PENDING rows with the cancellation, then sent to Razorpay with the refund id as the
  idempotency key (a retry can never refund twice). A lease stops two workers sending one refund; a job retries
  outages (`REFUND_RETRY_MINUTES`); permanent rejections become FAILED and show in the audit log (`refund.failed`) for a human.
  Razorpay's own "processed" webhook completes refunds that were still pending.
- **Messages use an outbox** (`NotificationLog`): the row is written in the same transaction as the event, sent by a dispatcher
  (`FOR UPDATE SKIP LOCKED`, safe on several instances), retried with backoff up to 5 times, and exactly-once per appointment and template.
  Reminders skip bookings made inside the 2-hour window (the confirmation just went out).
- **The app always talks to the database in UTC** (set on every connection). The integration tests run against a database set to Asia/Kolkata on purpose to keep that true.
- **Production databases must use UTF-8** (Neon and RDS do). The test database is created as UTF-8 explicitly.
- Refund percentages are of the amount paid; the gateway's fee is not returned by Razorpay and stays with the platform.

### Blood banks, donors and requests (how it stays safe)

- **MediQ connects people and never handles blood.** Every blood screen and the terms say so. The platform does not
  record units collected or issued, only what a bank reports as stock, and says how old that figure is.
- **No coupons.** An earlier plan had donations issue a single-use coupon that staff redeem. That was removed: a donation
  is a record (date, bank, confirmed group, amount) that sets the donor's waiting period. There is nothing issued to the
  donor, nothing to redeem and no coupon endpoint (a test fails if one is ever added).
- **Donations come only from staff.** `POST /blood-bank/donations` is available to blood bank staff of a **verified** bank;
  a donor cannot record their own. The waiting period and age limits are checked inside the same transaction that
  records it (with a per-donor lock), so two staff members recording the same donor at once get one donation and one
  refusal. Staff find a donor by phone: the answer is the same for "no account" and "not a donor", and each look-up
  is audited (with a masked number). The donor gets an SMS for every donation, so a wrong entry is noticed.
- **The waiting period** is `DONOR_GAP_DAYS_MALE` (90) for men and `DONOR_GAP_DAYS_OTHER` (120) for women and anyone who did
  not say; age limits are `DONOR_MIN_AGE`/`DONOR_MAX_AGE`. A donor in their waiting period is not alerted and cannot say
  "I can help". Whoever records a donation sets the donor's blood group to the one the bank's test found.
- **Who is alerted** (`modules/blood/matching.ts`, a pure and tested module): donors of **exactly** the requested group, available,
  eligible, not the person asking, within the chosen radius (or in the same city when either side has no coordinates),
  nearest first, at most `BLOOD_MAX_DONORS_ALERTED`, and nobody more than `BLOOD_MAX_ALERTS_PER_DONOR_PER_DAY` times a day.
  Verified blood banks nearby (up to 10) are alerted too. The request, the list of who was alerted, the queued SMS and
  the audit entry are **one transaction**: no alert is sent for a request that was not saved, and none is sent twice.
- **Phone numbers are shown only when someone chose to share them.** Donors never see the requester's number, only the
  hospital, city, units and first name. The requester sees a donor's number **only** while that donor's "I can help"
  stands **and** the request is open; closing, expiry or the donor withdrawing hides it again. A requester sees first
  names only.
- **The requester has no account.** Their phone is proved with a code, and the request page is opened with a secret key
  returned once and stored only as a keyed hash. It is sent in a header (never a URL, so it cannot reach logs or be shared by
  accident). If it is lost, a code to the same phone issues a new key and the old one stops working. "Find my request" answers the same
  whether or not a number has a request, and sends nothing if it has none, so it cannot be used to learn who asked for blood.
- **Abuse limits:** a code is needed for every request; one number can make 3 requests a day and cannot repeat an open
  request for the same group and hospital; every public endpoint has a per-address limit (these send SMS, which costs
  money); the admin can stop a request; a closed request loses the requester's name, number and note after
  `BLOOD_REQUEST_RETENTION_DAYS` (90).
- **Verification of banks:** a bank cannot be listed, alerted or operate until the admin approves it. Name and licence are
  locked once verified, so a listed bank cannot quietly become another. Blocking a bank signs its staff out at once.
- **Erasure and export** include donors: the donor profile, answers and requests made with the phone number go; the bank
  keeps its donation record without a link to a person.

### Hardening, monitoring and privacy (how it stays safe)

- **The route inventory is the source of truth.** `apps/api/src/docs/route-inventory.ts` walks the live Express
  routers (routers are attached with `mount()` so full paths are known; the login, role and rate-limit middleware
  carry markers). The security tests, the API reference and `pnpm routes` all read it, so a new endpoint cannot be
  forgotten: it must be in the public list or behind a login and a role, and it must be documented.
- **Statistics definitions** (so the numbers can be argued about): bookings count by **visit date** and exclude
  unpaid holds and expired ones; the cancellation rate is cancelled / all bookings; the no-show rate is
  no-shows / (seen + no-shows). Online money counts on the day it was **paid**, refunds on the day they were
  **processed**, per currency. **Commission** is MediQ's fee on the money kept after refunds (a fully refunded
  payment earns none). **Cash at the desk** is reported separately and carries no commission. "Refunds still to
  reach patients" is everything pending or failed right now, not limited to the period.
- **Erasure** keeps the appointment, fee, payment and refund rows (the hospital and tax law need them) but removes
  everything identifying: name, phone, date of birth, free text, message recipients and variables, and device and IP
  records; every session ends at once. It takes the same per-patient lock as booking, so a booking cannot slip in
  while it runs, and it refuses while an appointment, a hold or a refund is open.
- **Error tracking sends no personal data:** the SDK is told not to collect user info, cookies, headers, bodies or
  query strings, and a scrubber removes the rest and masks numbers and emails in text. Expected API errors are never
  reported.
- **UTC sessions:** every database connection is set to UTC before use (the app is independent of the database's own
  time zone). This needs a direct connection or a session-mode pooler: see `docs/DEPLOYMENT.md`.

### Operations: desk, queue, slips (how the clinic day works)

- **One desk API for staff.** `/desk/*` serves the receptionist and the doctor. The hospital always comes from the
  login. A doctor login is pinned to their own doctor record: asking for another doctor's list or slips is a 404.
- **Walk-ins use the same engine as online bookings.** They take the same slot lock, so a walk-in and an online
  patient can never take the same seat, and the token is the next integer for that doctor and day, inside the
  transaction. A walk-in is a patient profile with no account (matched by name and phone within that hospital), with
  commission 0 and, if paid at the desk, a `CASH` payment that records who took it. The patient's phone number is
  optional; the SMS is sent only when one is given.
- **Status changes are serialised per doctor and day** (an advisory lock), so two people tapping Start at once cannot
  both put a patient in the room. Only one patient can be `IN_PROGRESS` per doctor; starting the next one while
  someone is still in asks whether to complete the current one first.
- **Cancelling at the desk** follows the same refund policy as online. Online payments are refunded through the
  gateway (queued, retried). **Cash refunds are recorded as paid back immediately** and the screen tells the
  receptionist to hand the money over.
- **The live queue** (`/q/{doctorQrToken}`) is polled every 5 seconds (no WebSocket server to run). The API caches
  the numbers for 2 seconds, so many phones watching one queue cost one database read. The page shows numbers only: no
  names, phones or ids. Estimated wait is **people ahead x the doctor's average consultation minutes**; people ahead
  who have not arrived yet are counted, because they keep their place until the doctor skips them.
- **Slips print data only.** A template stores each field's position in **millimetres** from the top-left of the
  paper, so it does not depend on screen size or printer. The generator (pdf-lib) draws just the text, one page per
  slip sized exactly to the paper, with Hindi supported. Long text shrinks to fit its box (down to 6 pt) and is then
  shortened with "…". **Calibration** is a shift in X/Y (±20 mm) applied to every slip. The editor's "Alignment
  sheet" adds a ruler and field boxes for checking against the pre-printed paper. A scan of the blank slip is only a
  backdrop in the editor, never printed. Printing is audit-logged (`slip.printed`).
- **Print at 100% / Actual size.** Browsers' "Fit to page" and default margins shift everything; the editor tells
  staff to turn them off.
- **Emergency finder** (`/emergency`) needs no login. It lists open hospitals nearest first (haversine distance),
  with the emergency line (or main phone), a Directions link and bed availability. Bed counts older than 24 hours are
  marked as not recently updated. The visitor's location is rounded to about 100 m before it is sent, is used for
  one request and is not stored.

### Growth features (how they stay correct)

- **Reviews** are tied to the appointment by a unique key (one per visit, even if two taps race) and a database check keeps
  the rating between 1 and 5. The public list shows `isPublished` reviews only; hiding sets that flag and records who and why.
  A hospital's report never changes what the public sees. Erasing a patient's account deletes their reviews.
- **Waitlist.** One entry per (doctor, day, person). A job (`jobs/waitlist.job.ts`, every `WAITLIST_INTERVAL_SECONDS`) tells the
  oldest waiting patients, at most `WAITLIST_NOTIFY_BATCH` and never more than the seats that are free and not already offered.
  Moving an entry from WAITING to NOTIFIED is one guarded statement, and the SMS has a unique key, so several API instances
  can run it and nobody is told twice. A booking transaction marks the person's entry BOOKED.
- **Search** narrows doctors in the database (words, place, speciality, gender, language, fee) and applies rating, availability and
  sorting in memory on at most 1000 doctors (`capped` tells the client to narrow the search). That is plenty for a city
  pilot; move it into SQL when one search regularly matches more.
- **Language.** `User.language` and the web's saved choice are separate on purpose: a visitor has no account. An SMS stores the
  language it was queued in, so switching later never changes a message already waiting. MSG91 sends the Hindi DLT template when
  `MSG91_HINDI_TEMPLATE_IDS` has one for that message, otherwise the English one. `pnpm --filter web check:i18n` fails if a Hindi
  text is missing or has different `{placeholders}`.
- **Plans** (`modules/subscriptions`). The state is worked out from the stored status and the dates (`subscription-rules.ts`), so
  nothing has to run on a schedule to expire a plan. Limits are checked inside the same transaction as the change, under an
  advisory lock, so two admins adding the last doctor at once cannot both succeed. Only **new online bookings** are stopped for a
  hospital that is not in good standing: a patient who already paid keeps their appointment, and the payment webhook still confirms.

### Turning on the emergency map (Google Maps)

The finder works without any key (list, call and directions buttons). To add the map:

1. In Google Cloud Console, enable **Maps JavaScript API** and create an API key.
2. Restrict the key: _HTTP referrers_ = your domain(s) (and `http://localhost:3000/*` for development), _API

3. Put it in `apps/web/.env.local` as `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY=...` and restart the web app.
4. Also set `NEXT_PUBLIC_SITE_URL` (your real domain) so printed QR codes carry the right address.

### Turning on real payments (Razorpay test mode)

1. razorpay.com > create an account > **Settings > API Keys > Generate Test Key**. Put the key id and secret in `apps/api/.env` as `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET`.
2. Razorpay must reach your API, so run a tunnel locally (for example `cloudflared tunnel --url http://localhost:4000` or ngrok) or use your deployed API.
3. **Settings > Webhooks > Add**: URL `https://YOUR-API/api/v1/webhooks/razorpay`, a secret of your choice (put the same value in `RAZORPAY_WEBHOOK_SECRET`), and tick
   `payment.captured`, `payment.failed`, `order.paid`, `refund.processed`, `refund.failed`.
4. Set `PAYMENT_MODE=razorpay` and restart the API. It refuses to start if a key is missing.
5. Go live later with live keys (separate key id, secret and webhook), after Razorpay's KYC. Settlement to hospitals (Razorpay Route) comes later; commission is already stored per payment.

## 7. Production notes

Full steps: [`docs/DEPLOYMENT.md`](docs/DEPLOYMENT.md) (Vercel + Render + Neon), [`docs/BACKUP-RESTORE.md`](docs/BACKUP-RESTORE.md)
and [`docs/PILOT-CHECKLIST.md`](docs/PILOT-CHECKLIST.md). In short:

- Serve the API from a subdomain of the web domain (`app.example.in` + `api.example.in`) and set
  `COOKIE_SECURE=true`, `COOKIE_DOMAIN=.example.in`, `CORS_ORIGINS=https://app.example.in`, `TRUST_PROXY=1`.
- Run `pnpm db:deploy` on release. Never run `db:seed` against production (the script refuses).
- Set `STORAGE_FOLDER=mediq-prod` so production photos never mix with development ones. Cloudinary keys are
  required in production.
- Set `PAYMENT_MODE=razorpay`, live Razorpay keys and webhook, and a real `SMS_PROVIDER`: the API refuses to start without them. The webhook URL must be HTTPS and reachable by Razorpay.
- `PAYMENT_MODE=mock` is rejected at startup in production. `pnpm test:integration` can also run against a Neon branch: set `TEST_DATABASE_URL`.
- Keep `DATABASE_POOL_MAX` × number of API instances under the database's connection limit.
